---
title: "Persistent Storage"
description: "Configure how Mneno saves and retrieves memories."
---

Mneno defaults to in-memory storage, but it also provides built-in support for local persistence via JSON files or SQLite databases.

## Storage Options

### In-Memory Storage

Best for tests, demos, and short-lived processes where persistence is not required.

```python
from mneno import MemoryClient
from mneno.storage import InMemoryMemoryStore

# Default behavior
client = MemoryClient()

# Explicitly using in-memory
client = MemoryClient(storage=InMemoryMemoryStore())
```

### JSON File Storage

Best for simple local development, configuration files, or when you want human-readable storage.

```python
from mneno.storage import JSONFileStorage

client = MemoryClient(storage=JSONFileStorage("data/memories.json"))
```

- **Pros**: Human-readable, easy to debug, easy to version control.
- **Cons**: Slower for large datasets (entire file is rewritten on every update; reads reload the latest committed snapshot under a local lock).

### SQLite Storage

Best for durable local applications and larger memory sets.

```python
from mneno.storage import SQLiteStorage

client = MemoryClient(storage=SQLiteStorage("data/mneno.db"))
```

- **Pros**: Fast, durable, handles larger memory sets efficiently.
- **Cons**: Not human-readable without a SQLite client.

## Switching Storage

You can easily switch storage backends without changing your application logic. All storage backends implement the same `MemoryStore` protocol.

```python
from mneno.storage import JSONFileStorage, SQLiteStorage

# To migrate, you can export from one and import into another
old_client = MemoryClient(storage=JSONFileStorage("data/old.json"))
payload = old_client.export_json()

new_client = MemoryClient(storage=SQLiteStorage("data/new.db"))
new_client.import_json("data/old.json")
```

## Custom Storage

If you need to support an external database (e.g., PostgreSQL, Redis, or a Vector DB), you can implement the `MemoryStore` protocol.

```python
from mneno.storage.base import MemoryStore
from mneno.models import Memory

class MyCustomStorage(MemoryStore):
    def add(self, memory: Memory) -> Memory:
        # Your implementation
        pass

    def get(self, memory_id: str) -> Memory | None:
        # Your implementation
        pass

    # ... and so on
```

Duplicate memory IDs are rejected by all built-in stores; use an explicit update to replace a record.
Deleting a memory also removes its ID from session membership. JSON write failures restore the cached committed state.
JSON storage coordinates cooperating local writers and rejects stale snapshots; see the transaction contract below.
SQLite refuses databases with a schema version newer than this implementation.


## Atomic batch capability (0.5.0)

All built-in stores expose `transaction()` as a context manager yielding an isolated `MemoryStore`. Mutate the yielded
store, not the original. A successful exit commits once; an exception before commit leaves the original snapshot intact.
Imports (all modes), restore, and compaction require this capability. Other SDK operations are not automatically batch
transactions. Custom implementations can opt into `mneno.storage.AtomicMemoryStore`; unsupported batch operations raise
`TypeError` before changing data. Implementations must provide real commit/rollback, not compensating writes.

```python
with client.store.transaction() as staged:
    staged.add(memory)
    staged.add_session(session)
```

In-memory transactions serialize cooperating threads on the same instance and validate before swapping memory/session
maps. SQLite uses `BEGIN IMMEDIATE` and one commit for the complete batch, including sessions. SQLite is recommended for
concurrent applications and larger stores; staged transactions currently read and rewrite the full snapshot.

JSON uses a stable `<filename>.lock` sidecar (do not remove it while clients run), a content-hash revision check, and a
unique temporary file in the same directory. It syncs the temporary file before atomic rename and the parent directory
after rename on POSIX. Reads refresh the instance snapshot. A stale transaction raises `StorageConflictError`: read the
latest state, recompute the operation, then retry. This is optimistic concurrency, not automatic merging. Standalone
`update()` remains whole-record replacement; use a transaction when deriving an update from the current record.

Failure before rename preserves the committed file and cached state. If directory sync fails after rename,
`StorageCommitError.committed` is `True`: the complete replacement is visible, but power-loss durability is uncertain.
Do not blindly retry that operation. No universal durability claim is made for network filesystems, noncooperating file
writers, hardware failure, or Windows directory sync. POSIX locks release automatically on process exit; Windows uses
standard-library byte-range locks, which may report contention timeout. Lock files persist intentionally.

Existing JSON/export envelopes (v1), SQLite schema (v2), and legacy datetime representations are unchanged. Legacy naive
timestamps mean UTC for instant comparisons. Aware dates whose UTC instant lies outside Python's year range retain their
offset for comparison rather than overflowing. Unsupported/malformed model values still raise validation errors.

See [the integrity milestone report](https://github.com/Mneno-AI/Mneno/blob/phase-a-core-stabilization/docs/engineering/phase-a/DATA_INTEGRITY_HARDENING.md)
for the backend guarantees, fault-injection tests, and compatibility notes.
